| Данные на клиенте | **TanStack Query 5** + **Zustand** | кэш серверных данных и его обновление по WS-событиям; Zustand — локальное состояние (звук, «быстро», выбор в инвентаре) |

| Бэкенд | **NestJS 12** на Fastify (ESM, сборка SWC) | модули под домены; DI позволяет подменять `PaymentProvider` / `WithdrawalProvider` / `PriceProvider` без переписывания; guards для ролей; WS-шлюзы; бизнес-логику легко тестировать |

| Валидация и контракты | **Zod 4**, схемы в `packages/shared` | одна схема даёт валидацию на бэке, типы на фронте и OpenAPI-документацию |

| Real-time | **Socket.IO** + Redis adapter / emitter | комнаты (лента игры, баттл, личные уведомления), переподключение, масштабирование на несколько инстансов; воркер шлёт события через Redis |
| Фоновые задачи | **BullMQ** | раунды баттлов по таймеру, outbox, выводы и их таймауты, финализация лидербордов, сверка ledger, статистика |
| Rate limit | **rate-limiter-flexible** (Redis) | лимиты по пользователю и по IP на игровые, платёжные и auth-эндпоинты |
| Provably fair | `packages/game-core` + **@noble/hashes** | один и тот же код считает результат на сервере и проверяет его в браузере |
| Логи | **pino** (JSON) | структурные логи с request-id |
| Тесты | **Vitest** (unit + интеграционные на реальных PostgreSQL/Redis), **Playwright** (e2e), **k6** (нагрузка) | конкурентные тесты баланса имеют смысл только на настоящей БД |
| Инфраструктура | **Docker Compose**: caddy, web, api, worker, migrate, postgres, redis | `docker compose up` поднимает всё; **Caddy** — единый вход: сайт, `/api` и `/socket.io` на одном домене → cookie first-party, без CORS |
| Файлы | `StorageProvider`: локальный диск (dev) / S3-совместимое хранилище (prod) | картинки кейсов, предметов, баннеров из админки |
| CI | GitHub Actions | lint, typecheck, тесты с сервисами PostgreSQL и Redis |

В контейнерах — Node.js 24 LTS. Точные версии фиксируются lock-файлом на этапе 1.

**Что рассматривал и почему нет:**
- *Только Next.js (API routes / server actions)* — нет нормальных долгоживущих WebSocket и фоновых воркеров, транзакционную логику баланса там держать неудобно → отдельный бэкенд.
- *Fastify без Nest* — легче, но модульную структуру и DI пришлось бы изобретать; для долгого проекта Nest даёт дисциплину.
- *Prisma* — отличная DX, но блокировки строк и агрегаты ledger всё равно уходили бы в сырой SQL; Drizzle ближе к SQL.
- *tRPC* — удобно внутри приложения, но неудобно для вебхуков платёжек и внешних интеграций; выбрал REST + общие zod-контракты.

## 2. Общая схема

```
                Браузер (mobile-first, 360px+)
                          │ HTTPS, один домен
                          ▼
                       Caddy
        ┌─────────────────┴──────────────────┐
        │ /*                                 │ /api/*, /socket.io/*
        ▼                                    ▼
  web (Next.js SSR) ── внутренний HTTP ──▶ api (NestJS: REST + Socket.IO)
                                             │          │
                                             ▼          ▼
                                        PostgreSQL ◀── Redis ◀──┐
                                             ▲                  │
                                             └──── worker (NestJS: BullMQ, cron, outbox,
                                                     движок баттлов, Redis emitter → клиенты)
```

- **web** — Next.js: SSR публичных страниц (главная игры, кейсы, предметы, FAQ, Provably Fair, правовые) и интерактивные клиентские части. Админка `/admin` — тот же app, отдельная группа маршрутов; доступ проверяется и при рендере, и в API.
- **api** — REST `/api/v1/*` и Socket.IO. Вся игровая логика и всё, что касается баланса, — только здесь.
- **worker** — тот же код NestJS, другая точка входа (`worker.ts`): очереди, движок баттлов, outbox, кроны.
- **migrate** — одноразовый контейнер: миграции и идемпотентные сиды; api и worker стартуют после него.

## 5. Ключевые механизмы

### 5.1 Гемы, баланс и ledger

**Внутренняя валюта — гемы**

- Все суммы на сайте — цены, баланс, ставки, выигрыши, бонусы, призы колеса, промокоды, история — только в гемах. 1 гем — минимальная единица, дробных гемов нет: в БД `bigint`, в коде `number` с проверкой `Number.isSafeInteger`, никаких float.
- Курс `gemsPerUsd` (сейчас 100 гемов = $1) — настройка `settings.currency` со стартовым значением из `.env`, а не константа в коде. Меняет его только админ, с записью в аудит. На балансы и цены, уже выраженные в гемах, смена курса не влияет — только на будущие пополнения и на импорт цен в долларах.
- Пополнение в любой валюте (доллар, рубль, гривна, крипта): `FxRateProvider` даёт курс валюты к доллару, сервер считает котировку `гемы = floor(сумма × курс к USD × gemsPerUsd)` плюс бонус. Пользователь видит итог в гемах до подтверждения оплаты; котировка фиксируется на несколько минут, и зачисление идёт строго по ней. Курсы считаются десятичной арифметикой, округление — вниз до целого гема.
- Цены каталога хранятся в гемах. Если CSV или `PriceProvider` отдают цену в долларах, она пересчитывается по текущему курсу при импорте (до ближайшего целого гема).
- Гемы не выводятся деньгами: операции «вывод баланса» в системе нет, выводятся только предметы. Сорвавшийся вывод возвращает предмет в инвентарь.
- Реальная сумма и валюта оплаты хранятся у пополнения и видны только в админке — для сверки с платёжным провайдером. Пользователь везде видит гемы.

**Ledger**

- `ledger_entries` — журнал только на добавление: тип, сумма со знаком, баланс после операции, ссылка на сущность (`ref_type` + `ref_id`), уникальный idempotency key, автор (для ручных корректировок — обязательная причина). UPDATE и DELETE запрещены триггером.
- `wallets.balance` — денормализованный баланс. Меняется только в той же транзакции, что и запись в ledger, под `SELECT … FOR UPDATE`; `CHECK (balance >= 0)`.
- Сверка: фоновая задача проверяет `balance = SUM(amount)` и `balance = balance_after` последней записи; расхождение — алерт в дашборде админки. Тесты запускают сверку после каждого конкурентного сценария.
- Предметы — не гемы. Их движение пишется в `inventory_events` (получен, продан, выведен, использован в апгрейде и т.д.) с ценностью в гемах на момент операции. Операции с балансом пишут ledger, с предметами — `inventory_events`, смешанные — оба журнала в одной транзакции. Так у каждой операции есть запись, а баланс считается только из ledger.
- Порядок блокировок (против дедлоков): кошелёк → предметы пользователя (по возрастанию id) → общие ресурсы (тираж кейса, баттл).
- Идемпотентность: каждый мутирующий игровой и платёжный запрос несёт заголовок `Idempotency-Key` (фронт генерирует UUID на одно нажатие). Ключ фиксируется в `idempotency_requests` в той же транзакции: повтор возвращает сохранённый ответ, параллельный дубль получает `409`.

### 5.2 Provably fair

- У пользователя активна пара сидов: **server seed** (32 случайных байта, в БД зашифрован AES-256-GCM, наружу виден только SHA-256 хэш), **client seed** (можно менять), **nonce** (растёт на каждую ставку).
- Случайное число: `HMAC_SHA256(key = serverSeed, msg = "{clientSeed}:{nonce}:{cursor}")` → первые 52 бита → `float ∈ [0, 1)`.
- Маппинг по режимам:
  - **кейс** — `ticket = floor(float × 10⁷)` → предмет по накопленным шансам ревизии кейса (шансы хранятся целыми в единицах 0,00001 %, сумма ровно 10 000 000);
  - **апгрейд** — победа, если `float < chance`;
  - **контракт** — множитель `k = kMin + (kMax − kMin) × float^γ` → целевая стоимость → предмет с ближайшей ценой (см. 5.4);
  - **колесо** — `ticket = floor(float × сумма весов)` → сектор;
  - **баттл** — у каждого баттла собственный server seed, хэш публикуется при создании; client seed баттла = SHA-256 от client seed'ов участников по слотам (у ботов — детерминированный от id баттла, сервер не может его подобрать); раунд `r`, слот `s` → `HMAC(serverSeed, "{clientSeed}:{r}:{s}")`; ничья — отдельный бросок `"{clientSeed}:tiebreak"`.
- Смена пары сидов раскрывает старый server seed — все результаты с ним становятся проверяемыми. Сид баттла раскрывается после его завершения.
- Открытие ссылается на неизменяемую ревизию содержимого кейса (`case_revisions`): правка кейса в админке не ломает проверку старых результатов.
- Страница Provably Fair: объяснение, текущий хэш / client seed / nonce, смена client seed, история раскрытых сидов, инструмент проверки любого результата (считает в браузере тем же кодом из `game-core`; по ID результата подставляет данные сам).

### 5.3 Конкурентность

- Все операции с балансом и предметами — одна транзакция `READ COMMITTED` с блокировкой нужных строк в фиксированном порядке (5.1).
- Тираж лимитированного кейса — атомарный `UPDATE … SET supply_used = supply_used + n WHERE supply_used + n <= supply_total RETURNING`.
- Кулдауны (бесплатный кейс, колесо, ежедневный бонус) — строка `user_cooldowns` под блокировкой.
- Последнее место в баттле — блокировка строки баттла.
- Лимиты промокода — блокировка строки промокода, счётчик активаций в той же транзакции.
- Тесты: десятки параллельных запросов (двойной клик, гонка двух вкладок, повтор с тем же ключом) против реальной БД; после каждого — инварианты: баланс ≥ 0, баланс = сумма ledger, предмет потрачен не более одного раза.

### 5.4 Математика режимов

- **RTP кейса** = Σ(шанс × цена предмета) / цена кейса. Одна функция из `game-core` — в редакторе админки на лету и на сервере.
- **Апгрейд:** `chance = min(maxChance, ставка / цена цели × (1 − комиссия))`; цель дороже ставки; шанс ниже `minChance` — запрет. Шанс хранится целым в миллионных долях.
- **Контракт:** множитель распределён со смещением к низу: `k = kMin + (kMax − kMin) · u^γ`, где `E[k] = kMin + (kMax − kMin) / (γ + 1)`. γ вычисляется так, чтобы `E[k] = 1 − комиссия`. Пример: диапазон 0,25×–4×, комиссия 10 % → γ ≈ 4,77, шанс получить больше вложенного ≈ 29 %. Итоговый предмет — ближайший по цене к `k × вложено` из пула (активные предметы игры с флагом «участвует в контрактах»). Фактический RTP на текущем каталоге админка показывает симуляцией.
- **Баттлы:** classic — бо́льшая сумма дропов забирает всё, crazy — меньшая; 2×2 — по сумме команды.
- **Фактический RTP по режимам** — из агрегатов `stats_daily` (ставки против выплат); целевой: апгрейд и контракт — `1 − комиссия`, кейсы — по их составу.

### 5.5 Real-time

- Socket.IO, комнаты: `feed:{game}`, `battles:{game}`, `battle:{id}`, `case:{id}` (остаток тиража), `user:{id}` (баланс, уведомления).
- Через WS клиент ничего не решает: все действия идут через REST (там rate limit, идемпотентность, транзакции), WS только доставляет события.
- Синхронные рулетки баттла: сервер присылает результаты раунда и момент старта `spinStartAt` по серверным часам; клиент поправляет смещение часов; опоздавший сразу видит итог раунда.
- Лента дропов публикуется с задержкой примерно на длительность анимации, чтобы не спойлерить рулетку; последние дропы каждой игры лежат в Redis.
- Онлайн — уникальные соединения с heartbeat в Redis.

### 5.6 Побочные эффекты через outbox

Игровая транзакция записывает доменное событие (`case.opened`, `upgrade.finished`, `deposit.succeeded`…) в `outbox_events`. Воркер раздаёт его обработчикам: XP и уровни, ачивки, лидерборды, лента, уведомления, статистика, реферальные начисления. При падении процесса ничего не теряется, а баланс не зависит от побочных эффектов.

### 5.7 Вход и сессии

- **Steam** — OpenID 2.0 с проверкой `check_authentication`, ник и аватар через Steam Web API. **Google** — OAuth 2.0 (code + PKCE + state). **Telegram** — Login Widget, проверка HMAC по токену бота и свежести `auth_date`. Протоколы реализуются напрямую, без устаревших passport-стратегий.
- Один аккаунт — до трёх способов входа. Привязка учётки, уже принадлежащей другому пользователю, — ошибка (без автоматического слияния).
- Access JWT на 15 минут (httpOnly cookie, содержит id сессии) + refresh-токен на 30 дней (httpOnly, в БД только хэш, ротация с обнаружением повторного использования). «Выйти со всех устройств» отзывает все сессии, отзыв проверяется через Redis сразу.
- CSRF: `SameSite=Lax` + double-submit токен на всех мутирующих запросах; вебхуки проверяются подписью.
- 18+: до подтверждения игровые эндпоинты недоступны; дата и IP подтверждения пишутся в БД.
- Роли `user` / `support` / `admin`; права проверяются guard'ами в API и при рендере `/admin`.

### 5.8 Игра в URL и данных

- `/{game}/…` (`/standoff2`, `/cs2`) — источник истины для страницы, ссылки шарятся. Cookie `game` и поле профиля запоминают выбор и используются для редиректа с `/`.
- Игровые данные в API: `/api/v1/games/{game}/…`. Кошелёк, профиль, уведомления — общие.
- Новая игра = строка в `games` + редкости, предметы, кейсы + (если нужно) реализация вывода. Страницы и режимы не меняются.

### 5.9 i18n

- next-intl, `messages/ru.json`, ключи сгруппированы по фичам. API возвращает коды ошибок (`INSUFFICIENT_BALANCE`), текст выбирает фронт. Уведомления хранятся как тип + параметры.
- Контент из админки (названия кейсов, редкостей, призов, баннеров, ачивок) — jsonb `{"ru": "…"}`: новые языки добавляются без изменения схемы.
- Суммы в текстах склоняются ICU-плюралом: `{n, plural, one {# гем} few {# гема} many {# гемов} other {# гема}}`; название валюты — тоже ключ i18n.
- Линтер запрещает «сырой» текст в JSX.

### 5.10 Дизайн-система

- Токены: фон `#0B0B0F`, поверхности `#15151B` / `#1B1B22` / `#24242E`, акцент `#C6FF00` (только CTA и акценты), текст белый и серые оттенки. Цвет редкости приходит из БД и подставляется в карточку CSS-переменной.
- Рубленые углы — утилиты на `clip-path` с двухслойной обводкой (clip-path обрезает обычный border).
- Шрифты (OFL, с кириллицей, раздаём сами): заголовки — **Tektur** (угловатый, «рубленые» формы, 400–900), текст — **Golos Text**. Запасной вариант для заголовков — Russo One.
- Логотип: `assets/brand/gunraid-logo.svg`. Эмблема (открытый кейс с прицелом) отдельно — фавикон, мобильный хедер, иконка PWA.
- Гемы: `GemIcon` — гранёный кристалл `#C6FF00`, отдельный SVG-компонент; `GemAmount` — число с разделителями разрядов и иконкой, стоит рядом с каждой суммой (баланс, цены, ставки, призы, история). Подсказка на балансе (hover / tap) и окно пополнения показывают курс «100 гемов = $1» — значение берётся из настроек.
- Компоненты: Button, IconButton, Card, ItemCard, CaseCard, Modal, BottomSheet, Tabs, Tooltip, Toast, Input, Select, Checkbox, Switch, Badge, GemIcon, GemAmount, Avatar, Skeleton, Progress, Countdown, EmptyState. Витрина компонентов `/dev/ui` (только в dev).
- Mobile-first от 360px: сверху хедер (логотип, переключатель игры, баланс, вход) и лента дропов, на телефоне снизу таб-бар (Кейсы, Апгрейд, Контракт, Баттлы, Профиль).
- Анимации: рулетка кейса, круговой спиннер апгрейда, «переплавка» контракта, синхронные рулетки баттла, колесо. Везде кнопка «быстро» и переключатель звука.
- Без логотипов, шрифтов и изображений Valve и Axlebolt; демо-картинки предметов — свои SVG-плейсхолдеры.

### 5.11 Безопасность

- Все входящие данные валидируются zod-схемами; ответы API тоже типизированы.
- Cookie `httpOnly`, `Secure`, `SameSite=Lax`; заголовки безопасности и CSP (с разрешением только для виджета Telegram).
- XSS: React экранирует вывод; markdown правовых страниц рендерится без HTML.
- Rate limit на все игровые, платёжные, auth-эндпоинты и отдельно жёсткий — на активацию промокодов (против перебора).
- Мультиаккаунты: журнал IP, device-id (долгоживущая cookie) и отпечатка браузера; в админке — «связанные аккаунты» и ручные флаги, без автоматических банов.
- Аудит-лог: все действия админов и все изменения баланса вне игровой логики.
- Секреты только в env; server seeds зашифрованы ключом из env.

### 5.12 Тестирование

- `game-core`: unit-тесты с фиксированными векторами provably fair; статистические тесты распределений (шансы кейса, апгрейд, контракт, колесо — средний возврат в пределах допуска).
- `api`: интеграционные тесты на реальных PostgreSQL и Redis (поднимаются docker compose): ledger, идемпотентность, конкурентные сценарии, машины состояний (баттл, вывод), RBAC.
- e2e (Playwright): сценарии раздела 16 ТЗ на мобильном вьюпорте.
- Нагрузка (k6): открытие кейсов, баттлы, WS-соединения.
- CI: lint, typecheck, тесты на каждый push.

### 5.13 Запуск и окружения

- `docker compose up --build` → сайт на `http://localhost:8080`; миграции и сиды применяются автоматически.
- Разработка с горячей перезагрузкой: `docker compose up postgres redis` + `pnpm dev`.
- `.env.example` содержит все переменные с комментариями; секретов в репозитории нет.

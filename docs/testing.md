# Тестирование

Четыре уровня проверок. Первые два гоняются в CI на каждый push, сквозные и нагрузочные — в отдельном workflow `E2E` (вручную и после слияния в `main`).

| Уровень | Где | Команда | Что проверяет |
|---|---|---|---|
| Unit | `packages/*`, `apps/web` | `pnpm test` | provably fair, выбор предмета, RTP, баттлы, колесо, контракт, розыгрыш груза; CSP, пути игр, страница груза (шанс, таймер, места), формы чисел в текстах грузов, у каждого типа записи, уведомления, источника дропа и кода ошибки есть текст (`i18n-coverage`) |
| Интеграционные | `apps/api/**/*.e2e.test.ts` | `pnpm test` | API на настоящих PostgreSQL и Redis: ledger, идемпотентность, конкурентные операции, все режимы, ивентовые грузы, бонусы, выводы, админка |
| Сквозные (E2E) | `tests/e2e` | `pnpm e2e` | критерии готовности (раздел 16 ТЗ) в браузере, десктоп и телефон |
| Нагрузка и конкурентность | `tests/load` | `pnpm load` | HTTP + WebSocket под нагрузкой, атаки на баланс, сверка ledger |

### Режим «пул из одного соединения»

```bash
TEST_DB_POOL_SIZE=1 pnpm --filter @gunraid/api test
```

Интеграционные тесты API с пулом PostgreSQL из одного соединения и таймаутом ожидания 3 с. Если код внутри транзакции берёт второе соединение пула (через `this.db` вместо `tx`), тест падает по таймауту, а не проходит случайно. Под нагрузкой такая ошибка — взаимоблокировка пула и полное зависание API (так и было найдено, см. [progress.md](progress.md)). Этот режим — отдельный шаг CI.

### Ивентовые грузы

Тестовая БД общая между запусками (`global-setup.ts` только мигрирует и сеет), поэтому каждый тест грузов создаёт
свой шаблон, а `afterAll` выключает свои шаблоны и приземляет их открытые раунды обычным путём — следующие запуски
не тратят на них проход тикера, сверки остаются чистыми.

- `modules/cargo/cargo.e2e.test.ts` — публичные ручки (список, детальная для гостя и игрока, 404), покупка
  (места подряд, запись `cargo_entry` с client seed и хэшем раунда), вход и 18+, нехватка гемов (откат вместе с
  ключом идемпотентности), повтор ключа, гонка 6 игроков за 3 места, лимит на игрока (в том числе параллельно),
  бесплатный груз (пополнение за N дней, без ledger, одно место) и условие уровня, приземление при распродаже
  (приз, лента, уведомление, XP, раунд №2), приземление по таймеру с частичной продажей и без продаж, раннее
  событие срока, покупка после срока и с чужим раундом, правка и выключение шаблона, выключенный приз,
  доказательство (пересчёт места функциями `game-core`), тикер `sweep()` (события приземлений доходят и при сбое
  открытия раундов), обязательный client seed, минимум продаж (возврат, `void_seat`), возврат по id раунда
  прописными (в ledger, ключе возврата и аудите — канонический id, сверка чистая), сбой приземления на последнем
  месте (SAVEPOINT: покупка остаётся, раунд приземляет воркер), настоящая ошибка БД при приземлении (в
  `last_land_error` и логах — код и причина из PostgreSQL, без SQL с id игроков и исходом), гонка покупок со сроком,
  XP, закрытая фаза, CHECK связи покупки и ledger и `reconcileCargo`.
- `modules/cargo/cargo-worker.e2e.test.ts` — `CargoWorkerModule` подключён к `WorkerModule`, `CargoHandlers`
  зарегистрирован в outbox (без него событие `cargo.deadline` молча считалось бы обработанным); раунд приземляется
  по событию outbox; упавшее событие хранит в `last_error` причину, а не SQL с параметрами; тикер открывает раунд
  активному шаблону без раунда.
- `common/pg-errors.test.ts` — `errorText`: из ошибки запроса drizzle (`Failed query: … params: …`) берутся только
  код и причина PostgreSQL.

## Сквозные тесты (Playwright)

Нужен поднятый стек и тестовый вход (`AUTH_DEV_LOGIN=true` — значение по умолчанию в `.env.example`):

```bash
docker compose up -d --build --wait
```

Браузер для Playwright (один раз):

```bash
pnpm --filter @gunraid/e2e exec playwright install chromium
```

```bash
pnpm e2e
```

Адрес — `E2E_BASE_URL` (по умолчанию `http://localhost:8080`; для `pnpm dev` — `http://localhost:3000`). Если браузеры Playwright не установлены, а Chromium есть в системе — `PW_CHROMIUM_PATH=/путь/к/chromium`. Отчёт с трассировкой падений в CI — артефакт `playwright-report`.

Проекты: `desktop` (1366×900, все сценарии) и `mobile` (Pixel 7, сценарии с тегом `@mobile`). Каждый тест создаёт нового игрока через тестовый вход, поэтому тесты не зависят друг от друга; файлы идут по порядку, последний — общая сверка ledger.

| Файл | Сценарии |
|---|---|
| `01-public` | главная обеих игр и переключатель игры, гость → вход (после окна фокус снова на кнопке), правовые страницы и FAQ, sitemap / robots / Open Graph / CSP, cookie-баннер, 404 |
| `02-player` | вход и выход через окно входа, подтверждение 18+, пополнение через окно оплаты и страницу тестового провайдера, открытие кейса и продажа, продажа из инвентаря, «уменьшить движение» (результат без долгой прокрутки); после каждого — баланс = сумма записей ledger |
| `03-modes` | апгрейд на гемы, контракт из трёх предметов, открытие кейса — каждый результат проверяется на странице Provably Fair после смены пары сидов |
| `04-battles` | баттл с ботом от создания до итога и проверка всех раундов |
| `05-bonuses` | промокод на гемы (один раз), колесо закрыто для нового аккаунта, вращение по промокоду, созданному в админке |
| `06-withdraw` | вывод CS2: заявка → одобрение оператором → обмен → отмена сделки возвращает предмет; новому аккаунту вывод недоступен |
| `07-admin` | комиссия апгрейда из настроек сразу действует на сайте, редактор кейса (живой RTP, сумма шансов 100 %), промокод из админки работает у игрока, ручная корректировка баланса с причиной и аудитом, права support, игрок не видит админку |
| `08-case-page` | страница кейса: соседние кейсы при x1 и их нет при x2+, копии кейса по выбранному количеству, переход стрелками и кликом по соседу (по кругу), стрелка с клавиатуры держит фокус, бесплатный кейс без выбора количества, поля карточек содержимого (тип, скин, цена, шанс, ссылка), «Недостаточно средств» и окно пополнения, число дорожек рулетки (x3 — три, x1 — лента), возврат сцены и фокуса на кнопку после окна результата; «Быстро» у профиля без быстрого режима — результат сразу, выбор не сбрасывается и сохраняется в профиль |
| `99-reconciliation` | баланс каждого кошелька = сумма записей ledger |

## Нагрузочный и конкурентный прогон

```bash
pnpm load
```

```bash
pnpm load -- --users 50 --duration 60 --sockets 500 --json load.json
```

Параметры: `--base` (адрес, по умолчанию `http://localhost:8080`), `--users` (игроки), `--duration` (секунды нагрузки), `--sockets` (WebSocket-подключения к ленте), `--game`, `--p95` (порог p95 открытия кейса, мс), `--json` (сохранить отчёт). Скрипт на Node без внешних инструментов (k6 и т. п. ставить не нужно).

Фазы:

1. **Подготовка** — игроки через тестовый вход (вход ограничен 30 в минуту с одного IP — скрипт ждёт), тестовое пополнение по $100.
2. **Смешанная нагрузка** — каждый игрок в цикле: открытие кейса (x1 / x3), продажа всего, апгрейд на гемы, контракт, баттл 1×1 с ботом, чтение главной / кейса / ленты / профиля / инвентаря. Параллельно N WebSocket-клиентов подписаны на ленту дропов. Ответы 429 — это работа лимитов (12 игровых действий за 3 с на игрока), не ошибка.
3. **Конкурентные атаки** — двойное списание (денег на K открытий, 8 параллельных запросов → ровно K), один idempotency key в 8 параллельных запросах и повторе → одно открытие и одно списание, двойная продажа одного предмета (из 6 — одна), один предмет в 6 параллельных апгрейдах (проходит один).
4. **Сверка** — `GET /api/v1/admin/ledger/reconciliation`: баланс каждого кошелька = сумма записей ledger = `balance_after` последней записи.

Прогон падает (код выхода 1), если есть ответы 5xx или сетевые ошибки, нарушен любой инвариант, не сошёлся ledger, не все баттлы доиграны воркером или p95 открытия кейса выше порога.

### Результаты

Стенд: `docker compose` на одной машине (4 vCPU, 16 ГБ), один экземпляр API и воркера, PostgreSQL и Redis в контейнерах; нагрузка через Caddy (`http://localhost:8080`).

**20 игроков × 30 с, 200 WebSocket** — 6 497 запросов, 215 rps:

| Операция | Кол-во | p50, мс | p95, мс | p99, мс |
|---|---:|---:|---:|---:|
| POST открытие кейса | 1 594 | 15 | 130 | 172 |
| POST апгрейд | 502 | 13 | 89 | 133 |
| POST контракт | 303 | 17 | 117 | 172 |
| POST продажа всего | 403 | 13 | 121 | 183 |
| GET главная | 603 | 3 | 42 | 63 |
| GET инвентарь | 885 | 6 | 53 | 87 |

Ошибок 5xx — 0; 200 из 200 WebSocket получили 462 800 событий ленты. Все конкурентные инварианты выполнены, расхождений ledger — 0.

**50 игроков × 60 с, 500 WebSocket** — 20 246 запросов, 336 rps:

| Операция | Кол-во | p50, мс | p95, мс | p99, мс |
|---|---:|---:|---:|---:|
| POST открытие кейса | 5 026 | 101 | 268 | 406 |
| POST апгрейд | 1 223 | 77 | 201 | 349 |
| POST контракт | 658 | 110 | 248 | 334 |
| POST создание баттла | 619 | 105 | 351 | 442 |
| POST продажа всего | 1 255 | 91 | 306 | 412 |
| GET главная | 1 898 | 15 | 86 | 232 |
| GET инвентарь | 2 407 | 25 | 104 | 190 |

Открыто 7 234 кейса, 601 баттл с ботами — все доиграны воркером; ошибок 5xx — 0; 500 из 500 WebSocket получили 2,2 млн событий ленты. Все конкурентные инварианты выполнены, расхождений ledger — 0. Генератор нагрузки работал на той же машине, что и стек, — на отдельном сервере запас выше.

**История:** первая попытка этого прогона «повесила» API (взаимоблокировка пула соединений, см. [progress.md](progress.md)); результаты выше — после исправления.

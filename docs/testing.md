# Тестирование

Четыре уровня проверок. Первые два гоняются в CI на каждый push, сквозные и нагрузочные — в отдельном workflow `E2E` (вручную и после слияния в `main`).

| Уровень | Где | Команда | Что проверяет |
|---|---|---|---|
| Unit | `packages/*`, `apps/web` | `pnpm test` | provably fair, выбор предмета, RTP, баттлы, колесо, контракт, розыгрыш груза; CSP, пути игр, страница груза (шанс, таймер, места, участник итога раунда), проверка груза на Provably Fair (пересчёт, подделки, условие закрытия, усечение и группы списка покупок), форма груза в админке (границы полей, ошибки API по полям, RTP, чужая правка при несохранённых своих, окно отмены раунда), формы чисел в текстах грузов, фильтры кейсов главной (`lib/case-filters`: поиск без учёта регистра и «ё» / «е», цена в любом порядке, уровень, витрина без бесплатных), покрытие текстов (см. ниже) |
| Интеграционные | `apps/api/**/*.e2e.test.ts` | `pnpm test` | API на настоящих PostgreSQL и Redis: ledger, идемпотентность, конкурентные операции, все режимы, ивентовые грузы, бонусы, выводы, админка |
| Сквозные (E2E) | `tests/e2e` | `pnpm e2e` | критерии готовности (раздел 16 ТЗ) в браузере, десктоп и телефон |
| Нагрузка и конкурентность | `tests/load` | `pnpm load` | HTTP + WebSocket под нагрузкой, атаки на баланс, гонка за места груза, сверка ledger и грузов |

### Режим «пул из одного соединения»

```bash
TEST_DB_POOL_SIZE=1 pnpm --filter @gunraid/api test
```

Интеграционные тесты API с пулом PostgreSQL из одного соединения и таймаутом ожидания 3 с. Если код внутри транзакции берёт второе соединение пула (через `this.db` вместо `tx`), тест падает по таймауту, а не проходит случайно. Под нагрузкой такая ошибка — взаимоблокировка пула и полное зависание API (так и было найдено, см. [progress.md](progress.md)). Этот режим — отдельный шаг CI.

### Ивентовые грузы

Тестовая БД общая между запусками: `global-setup.ts` мигрирует, сеет и помечает обработанными события outbox,
оставшиеся от прошлых прогонов (воркера в тестах нет — сотни сроков раундов вставали бы в очередь перед событиями
новых тестов). Каждый тест грузов создаёт свой шаблон; `afterAll` в `cargo.e2e` выключает свои шаблоны и приземляет
их открытые раунды обычным путём, в `cargo-admin.e2e` — выключает шаблон, отменяет открытый раунд и отправляет
шаблон в архив. Следующие запуски не тратят на них проход тикера, сверки остаются чистыми.

- `modules/cargo/cargo.e2e.test.ts` — публичные ручки (список, детальная для гостя и игрока, 404), покупка
  (места подряд, запись `cargo_entry` с client seed и хэшем раунда), вход и 18+, нехватка гемов (откат вместе с
  ключом идемпотентности), повтор ключа, гонка 6 игроков за 3 места, лимит на игрока (в том числе параллельно),
  бесплатный груз (пополнение за N дней, без ledger, одно место) и условие уровня, приземление при распродаже
  (приз, лента, уведомление, XP, раунд №2), приземление по таймеру с частичной продажей и без продаж, раннее
  событие срока, покупка после срока и с чужим раундом, правка и выключение шаблона, выключенный приз,
  доказательство (пересчёт места функциями `game-core`), тикер `sweep()` (события приземлений доходят и при сбое
  открытия раундов), обязательный client seed, минимум продаж (возврат, `void_seat`), возврат по id раунда
  прописными (в ledger, ключе возврата и аудите — канонический id, сверка чистая), сбой приземления на последнем
  месте (SAVEPOINT: покупка остаётся, раунд приземляет воркер), настоящая ошибка БД при приземлении (в
  `last_land_error` и логах — код и причина из PostgreSQL, без SQL с id игроков и исходом), гонка покупок со сроком,
  XP, закрытая фаза, CHECK связи покупки и ledger и `reconcileCargo` (в том числе оплата ≠ цена места × мест:
  недоплата и бесплатные места в платном раунде).
- `modules/cargo/cargo-worker.e2e.test.ts` — `CargoWorkerModule` подключён к `WorkerModule`, `CargoHandlers`
  зарегистрирован в outbox (без него событие `cargo.deadline` молча считалось бы обработанным); раунд приземляется
  по событию outbox; упавшее событие хранит в `last_error` причину, а не SQL с параметрами; тикер открывает раунд
  активному шаблону без раунда.
- `modules/cargo/cargo-admin.e2e.test.ts` — админка грузов: support и игрок получают 403 на всех ручках, гость — 401,
  ничего не меняется; проверки приза (другая игра, выключен), занятого slug (в том числе архивным грузом), лимита и
  минимума продаж (не больше мест), бесплатный груз сохраняется с лимитом 1; создание активного груза — раунд №1 со
  снимком и `cargo:round`, аудит `cargo.create`; правка во время раунда — со следующего раунда (новый приз в
  `next`), аудит `cargo.update` до и после; выключенный груз доигрывает раунд, включение открывает раунд сразу;
  отмена (D33): точные возвраты по одной записи `cargo_refund` на игрока, `refunded_at`, публичное место «выиграло бы»
  (пересчёт `game-core`), аудит с причиной, уведомления, без XP, следующий раунд; гонки отмены — две отмены
  (200 + 409), отмена приземлившегося (409), короткая причина (400), покупка против отмены (деньги сходятся в обоих
  исходах) и повтор отмены, когда покупка прошла между чтением платящих и блокировкой раунда (с
  `TEST_DB_POOL_SIZE=1` пропускается: нужны две транзакции сразу); история раундов (фильтр, страницы) и детальная
  раунда с участниками; сверка (D39); архив (D37) — только без открытого раунда, скрыт из списка, только чтение,
  раунд больше не открывается, slug остаётся занятым; метки проблем `LANDING_STUCK` (с числом попыток и причиной),
  `PRIZE_INACTIVE`, `PRIZE_GAME`, `NO_ROUND` и RTP при текущих продажах; id из адреса прописными (аудит, ledger и
  сверка получают канонический id); дашборд (D13) — режим «Грузы», призы бесплатных грузов уменьшают GGR; адрес
  (slug) после создания не меняется (409), и сид после попытки переименовать сидовый груз ничего не создаёт заново;
  уведомление о возврате после «выключить → отменить → архив» ведёт на открывающуюся проверку раунда; NUL и
  одиночные суррогаты в названии, картинке, причине отмены и бана, строке поиска — 400, а не 500.
- `modules/feed/feed.e2e.test.ts` тикает воркер, пока событие открытия кейса этого игрока не обработано, — тест не
  зависит от числа чужих событий в очереди.
- `common/pg-errors.test.ts` — `errorText`: из ошибки запроса drizzle (`Failed query: … params: …`) берутся только
  код и причина PostgreSQL.
- `common/zod.test.ts` — `ZodPipe` отклоняет строки с NUL и половиной суррогатной пары (в том числе в ключах и на
  любой глубине — без рекурсии), эмодзи пропускает.

### Покрытие текстов (i18n)

Интерфейс показывает значения общих перечислений текстом из `apps/web/messages/ru.json`; новое значение без ключа
показалось бы игроку ключом или «Неизвестной ошибкой». Поэтому:

- `apps/web/src/lib/i18n-coverage.test.ts` — у каждого типа записи ledger (`history.types`), типа уведомления,
  источника дропа ленты (`topBar.sources`, в том числе `cargo`) и кода ошибки (`errors.*`, в том числе `CARGO_*`) есть
  текст. Исключения — три старых кода админки без текста (`CSV_INVALID`, `CASE_ODDS_INVALID`, `REASON_REQUIRED`):
  известный долг, новые коды в этот список не добавляются.
- `apps/web/src/app/admin/cargo/cargo-form.test.ts` («тексты админки грузов») — у каждой метки проблемы
  (`ADMIN_CARGO_ISSUES`), статуса и причины закрытия раунда, вида картинки и ошибки формы есть текст в
  `admin.cargo.*`, у режима «Грузы» — название в дашборде; падежи после чисел.
- `apps/web/src/lib/cargo-messages.test.ts` и раздел «тексты» в `cargo-proof.test.ts` — формы чисел в текстах
  страницы груза и проверки (ICU `plural`), описание формулы на странице проверки совпадает с тем, что считает
  `game-core`.

## Сквозные тесты (Playwright)

Нужен поднятый стек и тестовый вход (`AUTH_DEV_LOGIN=true` — значение по умолчанию в `.env.example`):

```bash
docker compose up -d --build --wait
```

Браузер для Playwright (один раз):

```bash
pnpm --filter @gunraid/e2e exec playwright install chromium
```

```bash
pnpm e2e
```

Адрес — `E2E_BASE_URL` (по умолчанию `http://localhost:8080`; для `pnpm dev` — `http://localhost:3000`). Если браузеры Playwright не установлены, а Chromium есть в системе — `PW_CHROMIUM_PATH=/путь/к/chromium`. Отчёт с трассировкой падений в CI — артефакт `playwright-report`.

**Грузы в e2e.** БД стенда живёт между прогонами, поэтому места покупаются только в своих тестовых грузах: админ
создаёт их через API (slug `e2e-…`, в конце списка, приз — самый дешёвый активный предмет), а `afterAll` (он
выполняется и после упавшего теста) выключает каждый груз `e2e-…`, отменяет его открытый раунд с возвратом гемов и
отправляет в архив — в том числе грузы прерванного прогона. Сидовые грузы только открываются, но не покупаются: иначе
места в их раундах копились бы до распродажи. Гонки сделаны детерминированными: чужая покупка уходит только после
того, как страница подписалась на комнату грузов (кадр socket.io `subscribe`); ответ своей покупки придерживается
`page.route`, пока итог раунда не дошёл по сокету; сокет рвётся и восстанавливается через `page.routeWebSocket`.
Соседей для стрелок страница берёт из кэша списка Next (до 15 с) — тест стрелок сначала ждёт, пока стрелки
сойдутся со списком API (после уборки прошлого прогона).

## Нагрузочный и конкурентный прогон

```bash
pnpm load
```

```bash
pnpm load -- --users 50 --duration 60 --sockets 500 --json load.json
```

Параметры: `--base` (адрес, по умолчанию `http://localhost:8080`; для `pnpm dev` — `http://localhost:4000`: сокеты идут прямо в API, dev-сервер Next их не проксирует), `--users` (игроки), `--duration` (секунды нагрузки), `--sockets` (WebSocket-подключения к ленте), `--game`, `--p95` (порог p95 открытия кейса и покупки места груза, мс), `--json` (сохранить отчёт). Скрипт на Node без внешних инструментов (k6 и т. п. ставить не нужно).

Фазы:

1. **Подготовка** — игроки через тестовый вход (вход ограничен 30 в минуту с одного IP — скрипт ждёт), тестовое пополнение по $100.
2. **Смешанная нагрузка** — каждый игрок в цикле: открытие кейса (x1 / x3), продажа всего, апгрейд на гемы, контракт, баттл 1×1 с ботом, чтение главной / кейса / ленты / профиля / инвентаря. Параллельно N WebSocket-клиентов подписаны на ленту дропов. Ответы 429 — это работа лимитов (12 игровых действий за 3 с на игрока), не ошибка.
3. **Конкурентные атаки** — двойное списание (денег на K открытий, 8 параллельных запросов → ровно K), один idempotency key в 8 параллельных запросах и повторе → одно открытие и одно списание, двойная продажа одного предмета (из 6 — одна), один предмет в 6 параллельных апгрейдах (проходит один).

   **Гонка за места груза** (`cargoRace`) — все покупатели груза стоят в очереди на одну строку раунда, а приземление идёт в транзакции последнего покупателя. Админ создаёт груз `load-<прогон>` в Standoff 2 (N = 20, цена места 10; игроков меньше 30 — N = игроков − 10, не меньше 2), все игроки нагрузки разом покупают по одному месту (свой client seed и idempotency key): успешных ровно N, места 1…N выданы по одному, итог раунда — в ответе последнего покупателя, прочие — 409 `CARGO_SEATS_LEFT` / `CARGO_ROUND_CLOSED`, 5xx нет; открыт раунд №2, победитель раунда №1 — среди купивших; p95 покупки — в отдельной таблице и не выше порога. Затем груз выключается, открытый раунд отменяется, груз уходит в архив.
4. **Сверка** — `GET /api/v1/admin/ledger/reconciliation`: баланс каждого кошелька = сумма записей ledger = `balance_after` последней записи; `GET /api/v1/admin/cargo-reconciliation`: у каждой платной покупки места — своя запись списания, возвраты — только у раундов с возвратом, места подряд.

Прогон падает (код выхода 1), если есть ответы 5xx или сетевые ошибки, нарушен любой инвариант, не сошёлся ledger, не все баттлы доиграны воркером, не сошлись места грузов или p95 открытия кейса (покупки места груза) выше порога.

### Результаты

Стенд: `docker compose` на одной машине (4 vCPU, 16 ГБ), один экземпляр API и воркера, PostgreSQL и Redis в контейнерах; нагрузка через Caddy (`http://localhost:8080`).

**20 игроков × 30 с, 200 WebSocket** — 6 497 запросов, 215 rps:

|---|---:|---:|---:|---:|
| POST открытие кейса | 1 594 | 15 | 130 | 172 |
| POST апгрейд | 502 | 13 | 89 | 133 |
| POST контракт | 303 | 17 | 117 | 172 |
| POST продажа всего | 403 | 13 | 121 | 183 |
| GET главная | 603 | 3 | 42 | 63 |
| GET инвентарь | 885 | 6 | 53 | 87 |

Ошибок 5xx — 0; 200 из 200 WebSocket получили 462 800 событий ленты. Все конкурентные инварианты выполнены, расхождений ledger — 0.

**История:** первая попытка этого прогона «повесила» API (взаимоблокировка пула соединений, см. [progress.md](progress.md)); результаты выше — после исправления.
